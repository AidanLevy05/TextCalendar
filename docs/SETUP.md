# Setup — credentials, keys, and exactly where they go

Read the summary table, then work through the four parts in order. Part 3
(Google) is the only place you download a real secret file.

## Summary: every private file in this project

| # | What | Where it comes from | Exact path | Mode |
|---|---|---|---|---|
| 1 | `config.toml` | you copy `config.example.toml` | `~/.config/signal-calendar-bot/config.toml` | `600` |
| 2 | signal-cli account keys | generated by device linking | `~/.local/share/signal-cli/` | `700` |
| 3 | Google OAuth **client secret** | downloaded from Google Cloud Console | `~/.config/signal-calendar-bot/client_secret.json` | `600` |
| 4 | Google **token** (refresh token) | generated by `scripts/google_oauth_setup.py` | `~/.config/signal-calendar-bot/token.json` | `600` |
| — | Ollama | **no key — it's local** | — | — |

**All four are already in `.gitignore`.** Nothing above should ever appear in
`git status`. Verify at any time:

```bash
git check-ignore -v ~/.config/signal-calendar-bot/client_secret.json  # if inside the repo
git status --short                                                     # must not list secrets
```

Create the directory once, owner-only:

```bash
mkdir -p ~/.config/signal-calendar-bot && chmod 700 ~/.config/signal-calendar-bot
```

> **Keep secrets outside the repo.** The paths above are under `~/.config`, not
> in the working tree, so a stray `git add -A` cannot reach them. The
> `.gitignore` patterns are a second line of defense for when you deviate.

## Part 1 — `config.toml` (file #1)

Not a key, but it holds your phone number, so it is gitignored.

```bash
cp config.example.toml ~/.config/signal-calendar-bot/config.toml
chmod 600 ~/.config/signal-calendar-bot/config.toml
$EDITOR ~/.config/signal-calendar-bot/config.toml
```

**You must change these two:**

```toml
[signal]
account = "+15555550123"            # ← YOUR number, E.164 (+countrycode, no spaces)
allowed_senders = ["+15555550123"]  # ← the same number

[general]
timezone = "America/New_York"       # ← your IANA timezone
```

Then tell the tools where it is, so you don't pass `-c` every time:

```bash
echo 'export SCB_CONFIG=$HOME/.config/signal-calendar-bot/config.toml' >> ~/.bashrc
source ~/.bashrc
```

The config is also searched at `./config.toml`,
`~/.config/signal-calendar-bot/config.toml`, then
`/etc/signal-calendar-bot/config.toml`, in that order.

Worth reviewing while you're in there — the model never sees these, code applies
them:

```toml
[confirmation]
timeout_seconds = 60      # your 60-second window; a lapsed proposal is destroyed

[scheduling]
day_start = "09:00"
day_end   = "21:00"
buffer_minutes = 15

[[scheduling.protected_blocks]]   # never scheduled over
name = "Jiu-jitsu"
days = ["mon", "wed", "fri"]
start = "18:30"
end = "20:00"
```

## Part 2 — Ollama (no key)

Local inference, so there is nothing to authenticate.

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3:8b        # ~5GB, fits the RTX 4060's 8GB
```

**On the MSI box (RTX 2060, 6GB)** pull a smaller model and change one config
value — no code changes:

```bash
ollama pull qwen3:4b
```
```toml
[ollama]
model = "qwen3:4b"
```

Keep the model resident in VRAM so the first message after an idle period
doesn't pay a full model load:

```bash
sudo systemctl edit --force ollama.service   # or use systemd/ollama.service
# Add:  [Service]
#       Environment=OLLAMA_KEEP_ALIVE=-1
```

Verify:

```bash
curl -s http://127.0.0.1:11434/api/tags | jq '.models[].name'
```

## Part 3 — Google Calendar (files #3 and #4)

This is the only real secret you download. Two files result: the **client
secret** (identifies the app) and the **token** (grants access to your
calendar). Roughly 10 minutes in the browser.

### 3.1 — Create a project

1. Go to <https://console.cloud.google.com/>
2. Project dropdown (top left) → **New Project**
3. Name: `signal-calendar-bot` → **Create**, then make sure it's selected

### 3.2 — Enable the Calendar API

1. **APIs & Services** → **Library**
   (<https://console.cloud.google.com/apis/library>)
2. Search **Google Calendar API** → **Enable**

Nothing works until this is enabled; skipping it produces a confusing
`403 accessNotConfigured` later.

### 3.3 — Configure the OAuth consent screen

**APIs & Services** → **OAuth consent screen**
(<https://console.cloud.google.com/auth/overview>)

1. User type: **External** → **Create**
   (*Internal* only exists for Google Workspace orgs. External is correct for a
   personal Gmail account, and being "external" with yourself as the only user
   is fine.)
2. App name: `signal-calendar-bot`; user support email: your address
3. Developer contact: your address → **Save and Continue**
4. **Scopes** → **Add or remove scopes** → paste each and add:
   ```
   https://www.googleapis.com/auth/calendar.events
   https://www.googleapis.com/auth/calendar.freebusy
   ```
   These are exactly what the bot requests — read/write events, plus
   availability. Not `calendar.readonly` (reads every calendar), not `calendar`
   (full access including settings and ACLs).
5. **Test users** → add your own Gmail address → **Save and Continue**

### 3.4 — Publish to Production ⚠️

**Do not skip this.** On the consent screen overview (or **Audience**), find
**Publishing status** and click **Publish app** → confirm.

> An External app left in **Testing** issues refresh tokens that **expire after
> 7 days**. The bot will work perfectly for a week and then start failing with
> `invalid_grant`, which looks exactly like a bug in your code. Publishing to
> Production makes refresh tokens long-lived.

You will *not* need Google verification: verification is only required for
sensitive/restricted scopes when you have real external users. With yourself as
the only user, Production + unverified is fine — you'll see an
"unverified app" warning during consent, and click **Advanced → Go to
signal-calendar-bot (unsafe)**. That warning is about *your own* app.

### 3.5 — Create the OAuth client and download the secret (file #3)

1. **APIs & Services** → **Credentials**
   (<https://console.cloud.google.com/apis/credentials>)
2. **+ Create Credentials** → **OAuth client ID**
3. Application type: **Desktop app** ← must be Desktop app, not Web
4. Name: `signal-calendar-bot-desktop` → **Create**
5. In the dialog, **Download JSON**. You get
   `client_secret_XXXXX-XXXXX.apps.googleusercontent.com.json` in `~/Downloads`.

**Move it to its exact path and lock it down:**

```bash
mkdir -p ~/.config/signal-calendar-bot
mv ~/Downloads/client_secret_*.apps.googleusercontent.com.json \
   ~/.config/signal-calendar-bot/client_secret.json
chmod 600 ~/.config/signal-calendar-bot/client_secret.json
```

The filename must be exactly `client_secret.json`, or point
`google.client_secret_file` in your config at wherever you put it.

It should look like this (a "desktop" app secret is not a password — but treat
it as private anyway):

```json
{"installed":{"client_id":"...apps.googleusercontent.com",
 "client_secret":"GOCSPX-...","redirect_uris":["http://localhost"], ...}}
```

If the top-level key is `"web"` instead of `"installed"`, you picked the wrong
application type — delete the client and redo 3.5 as **Desktop app**.

### 3.6 — Mint the token (file #4)

```bash
cd ~/TextCalendar
source .venv/bin/activate
python scripts/google_oauth_setup.py
```

A browser opens. Sign in, click through the unverified-app warning
(**Advanced → Go to … (unsafe)**), and grant both scopes. The script writes:

```
~/.config/signal-calendar-bot/token.json     (mode 0600, written atomically)
```

**This is the sensitive one** — it contains a refresh token granting ongoing
access to your calendar. It is gitignored, created `0600`, and never logged.

Confirm:

```bash
ls -l ~/.config/signal-calendar-bot/token.json     # → -rw------- 
python -m signal_calendar_bot doctor               # → google freebusy PASS
```

**Headless MSI box:** run `google_oauth_setup.py` once on a machine with a
browser using the same config, then copy `token.json` across and re-apply
`chmod 600`. The refresh token isn't tied to the machine.

## Part 4 — signal-cli (file #2)

There is **no key to download** here. You link signal-cli to your existing
Signal account as a secondary device — same as Signal Desktop. **No second
phone number.** The linking generates the credential; your phone stays primary.

### 4.1 — Install

```bash
# Check the latest version at https://github.com/AsamK/signal-cli/releases
export SIGNAL_CLI_VERSION=0.13.12
wget "https://github.com/AsamK/signal-cli/releases/download/v${SIGNAL_CLI_VERSION}/signal-cli-${SIGNAL_CLI_VERSION}.tar.gz"
sudo tar xf "signal-cli-${SIGNAL_CLI_VERSION}.tar.gz" -C /opt
sudo ln -sf "/opt/signal-cli-${SIGNAL_CLI_VERSION}/bin/signal-cli" /usr/local/bin/
signal-cli --version
```

### 4.2 — Link as a secondary device

```bash
signal-cli link -n "legion-calendar-bot" | tee /dev/tty | qrencode -t ANSIUTF8
```

Or use the helper: `./scripts/link_signal.sh "legion-calendar-bot"`

A `sgnl://linkdevice?...` URI prints and renders as a QR code. On your phone:

**Signal → Settings → Linked devices → Link new device → scan the QR code**

The command exits once linking completes. Your identity keys are now in:

```
~/.local/share/signal-cli/          ← file #2, gitignored
```

**Protect it — this directory is equivalent to your Signal account:**

```bash
chmod -R 700 ~/.local/share/signal-cli
```

Leaking it lets someone read and send your Signal messages. Never commit it,
never copy it into the repo, never put it in a backup that syncs to a cloud
service unencrypted.

### 4.3 — Verify, then run as a daemon

```bash
signal-cli -a "+15555550123" receive     # send yourself a Note to Self; it should print
```

Then install the units (edit the paths and number inside each first):

```bash
mkdir -p ~/.config/systemd/user
cp systemd/*.service ~/.config/systemd/user/
$EDITOR ~/.config/systemd/user/signal-cli.service          # your number, signal-cli path
$EDITOR ~/.config/systemd/user/signal-calendar-bot.service # your repo path

systemctl --user daemon-reload
systemctl --user enable --now signal-cli.service
systemctl --user status signal-cli.service
```

Keep the units running after logout (essential for the headless 24/7 box):

```bash
sudo loginctl enable-linger "$USER"
```

## Part 5 — Start the bot

```bash
python -m signal_calendar_bot doctor      # everything should PASS
systemctl --user enable --now signal-calendar-bot.service
journalctl --user -u signal-calendar-bot -f
```

Text yourself in **Note to Self**:

```
what's on thursday
lunch with dan thursday
```

The second one proposes a slot and waits 60 seconds for `yes`.

## Troubleshooting

**`invalid_grant` after about a week** — the consent screen is still in Testing.
Go back to 3.4, publish to Production, then re-run
`python scripts/google_oauth_setup.py`.

**`403 accessNotConfigured`** — the Calendar API isn't enabled (3.2).

**`redirect_uri_mismatch`** — the OAuth client is a *Web* app, not *Desktop*.
Redo 3.5.

**Bot never replies, unit looks healthy** — this is the silent websocket death
the heartbeat exists for. Check the log for `heartbeat missed`. Manually:
`systemctl --user restart signal-cli.service`.

**Bot replies twice to one message** — dedupe isn't persisting. Check that
`general.data_dir` is writable and `state.db` exists there.

**`No usable Google credentials`** — `token.json` is missing (3.6) or its path
doesn't match `google.token_file`.

**Model returns garbage / intents unparseable** — the model is too small or
`num_ctx` too low. Try a larger model, or raise `ollama.num_ctx`. The daemon
retries once with the validation error appended, then asks you to rephrase.

**Undo everything the bot created:**

```bash
python -m signal_calendar_bot purge
```

Backed by the `source = "signal-bot"` tag on every created event. Nothing else
on your calendar is touched.

## Rotating and revoking

| To revoke | Do this |
|---|---|
| Google access | <https://myaccount.google.com/permissions> → signal-calendar-bot → Remove. Then `rm ~/.config/signal-calendar-bot/token.json` |
| Signal access | Phone → Signal → Settings → Linked devices → unlink the device |
| A leaked client secret | Cloud Console → Credentials → delete the OAuth client, redo 3.5, re-run 3.6 |

If you ever commit a secret by accident, revoke it first (above) — rewriting git
history does not un-leak it.
